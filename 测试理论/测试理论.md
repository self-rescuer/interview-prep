
# 测试理论面试题

## 1. 软件测试的目的是什么？

主要是找出软件里的缺陷，保证交付出去的产品质量过关。测试不能证明软件没有 bug，但能尽量把问题提前发现，降低修复成本和上线风险。

## 2. 软件测试的生命周期包含哪些阶段？
需求分析 → 测试计划 → 用例设计 → 执行 → 缺陷跟踪 → 报告 → 回归

## 3. 黑盒测试和白盒测试的区别是什么？各适用于什么场景？
黑盒测试不看代码，只关心输入和输出对不对，比如功能测试、系统测试。白盒测试要看代码逻辑，验证分支、条件有没有覆盖到，比如单元测试。

两者不是对立的，实际工作中经常结合用。

## 4. 测试用例设计方法有哪些？请分别举例说明
等价类划分法：例如测用户名，可以分为合法用户名，非法用户名，用户名为空三个等价类
边界值分析法：例如测试账号id长度限定为10~18位，测试9，10，11，17，18，19
场景法：在测试注册功能时，测几个场景，1.正常注册成功2.用户名不合法，注册失败3.密码长度不合格，注册失败4.用户名为空5.密码为空
错误推断法：例如推测登录过程中容易出错的情况，例如密码错误或者账号长度有误
## 5. 什么是等价类划分？请以“登录密码”为例设计等价类
就是把输入范围分成几个等价类，同一类里的值效果是一样的，所以每类选一个代表值测就够了。

假设密码规则是“6-18位，必须同时包含数字和字母”：

有效等价类：6-18位含数字和字母，比如 abc123

无效：纯数字，比如 1234567

无效：纯字母，比如 abcdefg

无效：长度不够，比如 ab12

无效：超过18位

无效：含特殊字符，比如 abc@123
## 6.边界值分析为什么重要？请以“用户名长度 6-20 个字符”为例，列出需要测试的边界值。
因为边界及附近的值最容易出现误差，需要测5，6，7，19，20，21
## 7.缺陷的生命周期是怎样的？一个 bug 从发现到关闭要经过哪些状态？
一个 bug 从被发现到关闭，大概走这几步：

新建 → 指派给开发 → 修复中 → 待验证 → 验证通过就关闭。

如果验证发现没修好，就重新打开。另外开发如果觉得不是 bug，可以拒绝；如果确认是 bug 但暂时不修，可以延期。
## 8. 严重程度和优先级的区别是什么？请举例说明“严重程度高但优先级低”的场景。
严重程度就是对整个系统的影响程度，优先级就是需要被修复的紧急程度，半年前才用一次的导出功能崩溃（严重程度高，但优先级低）
## 9. 什么是回归测试？什么时候需要做回归测试？自动化测试在回归中起什么作用？
就是代码改了之后，把之前的测试用例重新跑一遍，确认没有引入新问题，也没破坏原来的功能。

一般在修 bug、加功能、重构代码、版本发布前都要做回归。

回归测试用例多、执行频繁，特别适合用自动化。每次代码提交后自动跑一遍，比人工快很多
## 10. 自动化测试的优缺点是什么？哪些场景适合自动化，哪些不适合？
优点：执行快、可以反复跑、适合回归测试，还能集成到 CI 里，每次提交自动跑。

缺点：前期投入大，要搭框架写脚本；维护成本高，页面改了脚本就要跟着改；也没法测 UI 体验和易用性这种需要人判断的东西。

适合自动化：需求稳定、重复执行的场景，比如回归测试、接口测试。
不适合：一次性的测试、探索性测试、需求频繁变的、需要看界面体验的。
## 11. 结合 django-crm 项目，你是怎么设计测试用例的？
我先看模型的字段和业务规则，再设计用例。比如 Company 模型有 full_name 长度限制和 unique_together 约束，我就设计了边界值测试（199、200、201字符）和唯一性测试（同一国家重名）。另外像 Lead 转化这种业务流程，我用场景法覆盖了不同分支——已有公司、新建公司、多个同名公司。

## 12. 你的测试项目中，哪些用了等价类划分？哪些用了边界值？
边界值用得比较多。比如 full_name 字段测了199、200、201三种长度。

等价类划分体现在权限测试里：把用户分成同部门、跨部门、管理员三类，每类验证不同的访问结果。还有 Request 的业务规则测试，把 contact 和 lead 的组合分成合法和非法等价类
